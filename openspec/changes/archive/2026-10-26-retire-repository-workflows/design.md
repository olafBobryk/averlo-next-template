# Design

## Context

See `proposal.md` for motivation and proposed capability paths. The audited router has fourteen entry rows and twenty concern references. Those references mix behavioral guarantees, dependency policy, component API teaching and operating instructions. Forms and loading have already migrated; the remaining references still point to them as a bridge.

Four operational skills invoke the router. `verify-skill-references.mjs` assumes its directory and fourteen-row table exist; composition tests also read individual references. Root and generated AGENTS, plugin documentation and positive assembly carry this dependency. Deleting the skill alone would leave both missing guidance and failing checks.

The worktree contains substantial prior work. This change's planning files are the only edits authorized by this proposal phase. Maintained form/loading specs, application code and the installed plugin cache remain untouched.

## Goals / Non-Goals

**Goals:** Give every existing rule a durable owner and make stock OpenSpec discovery sufficient for behavioral contracts. Retire the local skill only after its consumers and executable checks use those owners. Keep generated projects independent and truthful to installed features.

**Non-Goals:** Recreate the router in AGENTS, a parent spec, an index or a custom schema. Move every pixel value or import path into behavioral specs. Introduce new variant-selection policy, providers, thresholds, authentication methods, production delivery or a broad runtime redesign. Remove useful Compose/Animate/Systemize/Contact operating workflows or their approval boundaries.

## Decisions

### 1. Keep authority split by the kind of rule

Behavior belongs in the seventeen proposed capabilities and the two existing lifecycle capabilities. Dependency direction, source topology and client/server boundaries belong in nearest AGENTS. Supported imports, variants, geometry, tokens and examples belong in Storybook owner contracts. Execution, intake, measurement, provisioning and evidence capture belong in canonical procedures or existing operational skills.

This preserves guidance without flattening everything into OpenSpec. A single repository-policy spec would mix unrelated change reasons and duplicate API/structural owners. Keeping the router as a facade would retain the extra invocation requirement the user wants to eliminate.

Root AGENTS and OpenSpec context will state this authority boundary concisely and point to standard discovery. They will not reproduce the fourteen-entry routing table. WORKFLOWS remains a names-only procedure menu. The change-local migration map is audit evidence, excluded from generated projects; it is not a permanent discovery index.

### 2. Organize independently changeable capabilities into explicit families

Keep forms, reads/loading and non-form actions as siblings under `data-lifecycle/`; cross-reference their boundaries. Interaction, identity, delivery, content and navigation each have their own related capabilities. Entity presentation, component contracts, content hierarchy and generator assembly have separate owners.

This follows the approved family-folder convention without introducing a parent contract that repeats child requirements. Existing form and loading requirement sections remain byte-for-byte unchanged. In particular, shimmer remains a component default, not a requirement. The deferred canonical button-variant spec remains deferred; existing variant API teaching still receives an owner destination.

### 3. Require a source-to-destination reconciliation before retirement

`migration-map.md` assigns the router and all twenty references to destination groups and lists retained exceptions and operational gates. `source-baseline.json` records hashes and section ranges of the exact audited sources. During apply, add destination anchors and verification evidence per source section; split mixed sections into clause rows where necessary. Every original normative clause must resolve to a concrete destination or a justified duplicate of a named requirement. A hash change requires re-review of that source before deletion.

The baseline is change evidence, not a custom OpenSpec schema or installed reference index. It avoids treating broad thematic similarity as proof of lossless migration. Existing owner text can satisfy a rule; copying a duplicate is unnecessary, but its exact anchor must be recorded.

### 4. Migrate in reviewable batches, retire atomically at the end

Use these apply batches in dependency order:

1. Lifecycle and interaction: actions, keyboard/overlays, responsive/motion; retain form/loading boundaries.
2. Identity and delivery: access/membership, private files, API transport, submission protection, configured contact delivery.
3. Routes and content: route identity, metadata, source resolution, media, marketing composition.
4. Shared presentation: content hierarchy, component contracts and entity presentation.
5. Generator integration: project assembly, applicable policy/procedure/test copies, generated instructions and profile omissions.
6. Retirement: dependent skills, plugin documentation, verification assumptions, link reconciliation and final deletion.

Until final retirement, old references become short links to the now-canonical destinations as each group is migrated. Do not preserve competing normative copies. Sync complete delta capabilities through stock OpenSpec, validate maintained specs and retain their verification evidence. Archive only after the whole approved change is complete. If applying only a selected batch, keep the change active and report the remainder explicitly.

### 5. Preserve operational skills and approvals

Compose keeps source classification, intake, reference-case boundaries, approved-header exclusions, measured human review and Visual Parity evidence. Animate keeps explicit motion ownership. Systemize Composition keeps confidence and shared-owner approval gates. Contact Form keeps recipient decisions, credential policy, per-project provisioning and intentional real-send authorization.

Their router calls become direct references to the applicable canonical specs/structural owners/procedures. Packaged skills must resolve those references against the target repository, not assume it is adjacent to the plugin installation. In a repository without the migrated contracts, report the missing contract and continue only within established scope; do not recreate the deleted router or invent equivalent policy. Installed cache copies are not edited or published by this migration.

Implementation inspection confirmed that private files expose an unconfigured policy/adapter boundary and contact/support expose fixture-only endpoints; no real storage or contact delivery adapter is installed. Consistent with the approved no-provider scope, verify their unavailable/no-delivery behavior and preserve future provider lifecycle cases as conditional procedures. Do not add providers to manufacture test coverage or claim those future paths were executed.

### 6. Preserve exact teaching outside behavioral requirements

Visual composition includes current dashboard shell geometry, account/organization menu placement, workspace scrolling, surface vocabulary, edge-alignment semantics, icon choices, neutral palette and contrast teaching. These must move to the appropriate layout, toolbar, surface, icon, input and tint owners; a generic grouping requirement is insufficient to preserve them.

Owner discovery also includes evidence order, variant-equivalence review, raw interactive-role inventory, public naming, wrapper justification and smallest client boundaries. Keep its procedural order in component guidance and existing evidence procedures; keep dependency/API rules at their actual owners. Do not invent the deferred app-wide button-selection policy under another name.

### 7. Positive assembly determines policy applicability

Replace unconditional whole-tree spec copying with explicit selected ownership where required. All UI-capable projects receive component/interaction/common hierarchy guidance; application profiles receive applicable identity/entity/action/navigation coverage; marketing profiles receive applicable public content/media/metadata coverage. Both receive only their installed form/loading test cases. Source-resolution modes remain truthful to static, ready and powered configurations. Contact-delivery guidance is conditional guidance for explicitly enabled delivery; it cannot imply that contact/support fixtures send email.

Keep `template/project-assembly` in the template only. Keep change history, audit baselines, plugin source and unrelated agent files out of generated instances. Copy stock OpenSpec integration independently and unchanged. Update config, copied docs, relative links, package-script ownership, positive manifest ownership and thin-start inventory together. Generated specs must have no dangling cross-reference to an omitted capability; include a legitimately shared dependency or narrow profile guidance instead of leaving an invalid reference.

### 8. Verification demonstrates behavior and ownership

Reuse existing deterministic verifiers and owner interactions. Add only missing scenario coverage at the appropriate server, component or browser boundary; do not write tests that merely repeat prose. `migration-map.md` records exact existing commands and proposed procedure homes. Browser checks use Preview and actual rendered boundaries, controlled failures and genuine server cases as applicable; fixture-only checks never send real email.

Refactor router-specific verification to retain generic skill-link, repository-path and command validation. Composition checks must protect retained source-intake, shell and approval boundaries at their new owners, not continue asserting a removed skill name or fourteen-row table. Make a targeted negative test demonstrate broken links or omitted required ownership still fail.

Run root contract/type/build checks plus the relevant family checks. Generate full and thin-start projects across full, app-only and marketing-only supported combinations, verify copied applicability/links and run installed-family coverage. Static/ready/powered content differences need assembly verification without provisioning live services. Distinguish prior reproducible failures from migration regressions; do not claim a blanket pass when a check fails.

## Risks / Trade-offs

- A behavior-oriented summary could lose exact defaults or exceptions → reconcile every source section to concrete owner anchors before deletion, including dashboard geometry and explicit approval rules.
- Seventeen capabilities can feel fragmented → group by families and use native discovery plus focused cross-references; no duplicate parent spec or new router.
- Existing policy could be accidentally strengthened → derive requirements from current references, preserve conditional scope and waivers, and seek a separate decision for genuine behavior changes.
- Specs alone do not prove runtime conformance → reuse meaningful tests and record evidence/gaps; repair only bounded approved scenarios.
- Plugin-relative links may work locally but fail after packaging → exercise packaged skill resolution against a generated independent project.
- Whole-tree copying may leak generator policy or dangling references → explicitly verify selected output ownership and link closure in all supported profile combinations.
- Dirty baseline or concurrent changes may invalidate source evidence → preserve unrelated edits, compare baseline hashes and re-audit changed sections before retirement.

## Migration Plan

1. Obtain review of this concrete proposal and selected apply scope. Implementation uses the standard apply skill and delegated batches as requested by the user.
2. Follow the batches above; complete each destination's contract, procedure and tests before replacing its bridge prose.
3. Update assembly and generate independent verification projects. Reconcile every source section and dependent consumer.
4. Remove the repository-local router directory only after reconciliation and relevant checks pass. Validate both the change and maintained specs, then archive through stock OpenSpec.
5. Handoff the canonical specs, procedures, actual check results and any verified UI links for runtime repairs. Plugin publication and installed-cache updates require a separate release task.

Rollback restores the removed router and consumers from the pre-retirement Git state together, retaining any already-valid destination specs as canonical and avoiding contradictory copies. No data migration, service cutover or deployment is part of this change.
