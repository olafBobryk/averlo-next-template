# Design

## Context

The canonical repo has nineteen maintained capabilities. Eighteen are shared/profile-selected; `template/project-assembly` is already excluded by the template-only root. Several shared specs mix production behavior with demos or assembly rules. See proposal.md for motivation and source-baseline.json for exact inputs.

## Goals / Non-Goals

Goals: explicit contract ownership, portable app-only inheritance, complete clause conservation and discoverable ordinary stock operations.

Non-goals: change runtime demo semantics, enable providers, change installed profile features, add routing skills/schemas or move historical archives to new identities. The independently authorized Next upgrade changes dependencies only.

## Decisions

1. Use `app/<existing-family>/<existing-capability>` for eighteen reusable capabilities; retain `template/project-assembly` and add `template/demo-behavior`. Compared with excluding every spec, this preserves intentionally inherited product-neutral behavior as requested. Compared with duplicating full specs into both trees, extraction keeps one normative owner per clause.
2. Transfer entity reset/no-external-write, fixture auth/storage truthfulness and contact/support demo-specific results into template/demo-behavior. Move form/loading assembly inheritance to project-assembly. Generic forms retain validation/recovery/safe login and explicit configurable success semantics. Production persistence and delivery are allowed through their real configured boundaries; app contracts do not prescribe a demo as their outcome.
3. Preserve every prior generic clause and scenario through namespace retirement plus ADDED replacements; retire old capability identities only after replacements validate. Set the stock retirement metadata explicitly. Correct cross-capability references; do not rewrite archived evidence to pretend it used current names.
4. Existing explicit manifest/surface ownership selects independent `app/` copies. Exclude all `template/` contracts/history. Generated config explains its own ownership without inheriting canonical-template context or unconditional no-delivery policy. Tests/procedures can honestly describe installed example forms until those examples are replaced.
5. Root/nearest AGENTS and stock `openspec list --specs`/`show` route agents to maintained contracts by changed behavior. No implicit routing skill, custom index or schema. Procedures remain behind the names-only WORKFLOWS menu; operational approval gates remain intact.

## Risks / Trade-offs

- Broken references after namespace moves: update live consumers, retain historical identities, verify links and independent packaged targets.
- Lost fixture safety when extracted: preserve all clauses/scenarios in the template owner and run unchanged browser cases. Existing source/test/owner disclosures remain accurate.
- Accidentally copied template context: verify generated absence of template specs and old identities, config ownership and app-reference closure across seven standard outputs with negative guards.
- Optional assistant/profile and aggregate baseline failures: report exact existing failures separately; do not weaken unrelated verifiers.

## Migration Plan

Capture baseline, construct deltas and clause mapping, sync through stock operations, update live consumers and positive assembly, run focused and generated checks, validate and archive. Rollback uses the change baseline and exact touched paths without resetting unrelated dirty work. Historical archives are immutable evidence; no provider or deployment rollout exists.
